# ADR-0002: Идемпотентность POST /inventory/fulfill по `order_id`

**Статус**: Принято
**Дата**: 2026-05-20
**Контекст**: US-B2B-10

## Проблема

POST `/api/v1/inventory/fulfill` уменьшает `reserved_quantity` у SKU при доставке. Канон требует идемпотентности **по `order_id`** (а не по обычному `idempotency_key`, как у `/reserve` и `/unreserve`): повторный вызов B2C с тем же заказом не должен списывать резерв повторно — иначе `reserved_quantity` уйдёт в минус.

## Рассмотренные варианты

1. **Отдельная таблица `fulfilled_orders`** с UNIQUE(order_id, sku_id) — записываем факт списания на пару (order_id, sku_id). Перед списанием use-case проверяет, какие пары уже зафиксированы, и пропускает их.
2. **Поле `last_fulfilled_order` на SKU** — для каждого SKU хранить последний обработанный order_id; пропускать, если он совпадает с входящим.
3. **Проверка по `reserved_quantity`** — если `reserved_quantity < quantity`, считать вызов повторным и игнорировать.

## Критерии

- **Double-deduction risk**: 1 — UNIQUE constraint на уровне БД гарантирует at-most-once для каждой пары; параллельные ретраи безопасны. 2 — работает только если порядок fulfill'ов — строго один-за-другим; невалиден при параллельных заказах с пересекающимися SKU. 3 — небезопасно: при двух разных order_id (разных заказах с одинаковым SKU) ошибочно считает второй повтором первого.
- **Complexity**: 1 — одна таблица, один UNIQUE, прямолинейный код. 2 — нужно атомарно сравнивать-и-обновлять поле; вырождается в (1) при многопользовательской нагрузке. 3 — минимальный код, но требует тщательной аргументации корректности и хрупок к сценариям рассинхронизации.

## Решение

Выбран **вариант 1: отдельная таблица `fulfilled_orders`** с UNIQUE(order_id, sku_id). В одной транзакции use-case: (a) читает уже зафиксированные пары для order_id, (b) для оставшихся items выполняет `SELECT ... FOR UPDATE` + UPDATE `reserved_quantity -= quantity` через InventoryRepository, (c) INSERT'ит в `fulfilled_orders`. UNIQUE-ограничение защищает от параллельных fulfill'ов с одним order_id (одна транзакция пройдёт, остальные получат IntegrityError и откатятся). Стоимость — одна дополнительная таблица; этого мы избегать не пытаемся, поскольку (2) и (3) допускают двойное списание.
