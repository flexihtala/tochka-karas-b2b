# ADR-0001: All-or-nothing реализация POST /inventory/reserve

**Статус**: Принято
**Дата**: 2026-05-20
**Контекст**: US-B2B-08

## Проблема

POST `/api/v1/inventory/reserve` обновляет `active_quantity` и `reserved_quantity` сразу у нескольких SKU. Если хотя бы один SKU не проходит проверку `active_quantity >= requested`, всё резервирование должно откатиться — иначе один SKU будет списан, а другие нет, и в B2C получится частично подтверждённый заказ.

## Рассмотренные варианты

1. **Single tx + `SELECT ... FOR UPDATE`** — открываем одну транзакцию, блокируем все строки SKU в детерминированном порядке, проверяем и обновляем. Параллельные reserve'ы сериализуются на конфликтующих строках.
2. **Оптимистическая блокировка + retry** — UPDATE с условием `WHERE active_quantity >= :qty`, проверяем rowcount, при конфликте — retry. Без явных блокировок.
3. **Двухфазный коммит (2PC)** — координатор готовит резерв на каждом SKU отдельно, при отказе — rollback. Избыточно для in-process одной БД.

## Критерии

- **Performance**: 1 — блокировки короткие (микросекунды), но сериализуют параллельные конфликтующие запросы. 2 — потенциально выше throughput для непересекающихся SKU, но при контеншене retry-цикл усложняет latency. 3 — самый медленный.
- **Complexity**: 1 — минимум кода, явная транзакционная граница. 2 — нужно реализовывать retry-логику и обрабатывать частичные успехи. 3 — несоразмерная сложность для in-process.

## Решение

Выбран **вариант 1: single tx + `SELECT ... FOR UPDATE`**. SKU-строки блокируются `with_for_update()` в порядке возрастания UUID (снижает риск deadlock'ов при пересечении), валидация и UPDATE происходят в одной транзакции; при failure InventoryConflictError откатывает транзакцию контекст-менеджером SQLAlchemy. INSERT processed_events для идемпотентности и outbox SKU_OUT_OF_STOCK события — в той же транзакции, что даёт атомарную idempotency.
