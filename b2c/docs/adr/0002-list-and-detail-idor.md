# ADR-0002: IDOR-protection в GET /orders/{id} — `filter(user).get(id)`

**Статус**: принято (US-ORD-02).

## Контекст

GET /api/v1/orders/{id} принимает `order_id` из URL. Без защиты любой
аутентифицированный покупатель мог бы дёрнуть чужой заказ просто перебором UUID
(IDOR — Insecure Direct Object Reference).

Канон (b2c-orders-flows.md, §"Authorization (IDOR prevention)") требует:
- `user_id` берётся **только из JWT** (никогда из query/body/headers).
- Чужой заказ возвращает **404**, а не 403 — чтобы не раскрывать существование
  чужих ресурсов через различающиеся коды ответа.

## Рассмотренные варианты

1. **`filter(user_id=...).get(id=...)`** на уровне репозитория — фильтрация
   ВНУТРИ SQL-запроса. Выбран.
2. `get(id)` → загрузить → проверить `order.user_id == jwt.user_id` в use-case.
3. Permission scope / Django Guardian-style — оверкилл для одного ресурса.

## Решение

`OrderRepository.get_for_user(order_id, user_id)` принимает оба идентификатора
и выполняет `WHERE id = ? AND user_id = ?` в одном SELECT. Возврат `None`
интерпретируется use-case как 404 `ORDER_NOT_FOUND` — без разницы, заказа нет
вовсе или он принадлежит другому пользователю.

## Обоснование

- **Защита на уровне SQL**: не существует кодпути, который случайно вернёт
  чужой заказ; ошибка в use-case (забыли проверку) физически невозможна.
- **Один запрос вместо двух** (SELECT + IF-check).
- **Канон-совместимо**: 404 единый для "нет" и "чужой" из коробки.
- **Тестируется напрямую**: `test_other_user_order_returns_404_not_403` бьёт
  в use-case без необходимости проверять roundtrip к роутеру.

## Что отбросили и почему

- **get + проверка в use-case** — рабочий, но создаёт два кодпути с одинаковым
  смыслом (одна функция fetch'ит, другая проверяет). Легко забыть проверку
  в новом use-case (cancel, mark_delivered) — здесь же логика на уровне SQL.
- **Permission scope** — нет требований для роли BUYER, кроме owner-фильтра;
  лишняя абстракция.
