# ADR-0001: Идемпотентность checkout — UNIQUE на orders.idempotency_key

**Статус**: принято (US-ORD-01).

## Контекст

POST /api/v1/orders должен быть идемпотентным: повторный запрос с тем же
`idempotency_key` (например, при двойном клике или ретрае на стороне фронта)
не должен создавать второй заказ и не должен повторно резервировать SKU в B2B.

Канон (b2c-orders-flows.md, §"Двойной клик checkout"):
> Если заказ с таким ключом уже существует -- возвращается существующий заказ
> (200, не 201).

## Рассмотренные варианты

1. **UNIQUE на orders.idempotency_key + IntegrityError catch** (выбран).
2. Отдельная таблица `processed_checkouts(idempotency_key, order_id)` —
   как `inbox` на B2B-стороне.
3. Redis-кеш с TTL.

## Решение

UNIQUE-индекс на `orders.idempotency_key` + double-check паттерн в use-case:

1. SELECT по idempotency_key. Если есть — возврат, статус 200.
2. INSERT Order + OrderItem атомарно. UNIQUE-нарушение → race detected →
   повторный SELECT (гарантированно вернёт строку, т.к. конкурент уже закоммитил).

## Обоснование

- **Один источник истины**: idempotency_key привязан к заказу и хранится вместе
  с ним, нет рассинхронизации между двумя таблицами.
- **Простота отката**: если заказ удаляется (в учебной БД), ключ освобождается
  автоматически.
- **Нет лишней инфраструктуры**: без Redis, без дополнительной таблицы.
- **Гонка обрабатывается**: SELECT перед INSERT снижает вероятность IntegrityError,
  а catch гарантирует корректность даже при race.

## Что отбросили и почему

- **Отдельная таблица** — даёт гибкость хранить ответ под ключом (как
  processed_events на b2b-inbox), но дублирует order.id и требует второй INSERT
  в той же транзакции. Для одного типа ключей (на заказ) overkill.
- **Redis** — лишняя зависимость в сервисе без других кеш-нужд, плюс
  TTL-окно создаёт окно гонки между истечением кеша и долгоживущим запросом.
